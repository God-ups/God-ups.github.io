# CAN 波形介绍与 CAN 协议帧解析

## 1. 先分清：CAN 总线 vs 跑在 CAN 上的协议

CAN 本身只规定**物理层 + 数据链路层**（ISO 11898）。日常说的 XCP on CAN、UDS on CAN、CANopen，都是**跑在 CAN 上的上层应用协议**，不是新的 CAN 总线。

汽车电子里最常用的是 **UDS on CAN** 和 **XCP on CAN**。

### 1.1 常见上层协议对照

| 名称 | 全称 / 标准 | 主要用途 | 关键点 |
| --- | --- | --- | --- |
| CANopen | CANopen / CiA 301 | 工业控制、车身子节点 | 基于 CAN 的应用层协议，PDO / SDO / NMT |
| UDS on CAN | Unified Diagnostic Services，ISO 14229 | 诊断、故障码、刷写 | 功能寻址 `0x7DF`，物理寻址 `0x7E0 → 0x7E8`；超过 8 字节走 ISO-TP（ISO 15765-2）拆帧 |
| XCP on CAN | Universal Measurement and Calibration Protocol，ASAM | 实时测量、在线标定 | 两个 CAN ID：CTO（命令）+ TO / DAQ（周期数据）；必须有 A2L 文件描述变量地址 |

### 1.2 UDS 与 XCP 的分工

| 项 | UDS on CAN | XCP on CAN |
| --- | --- | --- |
| 目的 | 诊断、刷写、故障码 | 实时测量、参数标定 |
| 典型工具 | 诊断仪、CANoe | INCA、CANape |
| 地址 | 功能寻址 `0x7DF` / 物理寻址 `0x7E0 → 0x7E8` | 两个 CAN ID：CTO（命令）+ TO（DAQ 数据） |
| 前置条件 | 无 | 需 A2L 描述文件与 ECU 匹配 |
| 多帧 | ISO-TP 拆装 | XCP 自带传输层 |

> 小结：CAN 只是总线，上面能跑的应用协议很多。

## 3. CAN 物理层基础

CAN（Controller Area Network）是汽车 / 工业常用的**多主、两线差分、无主机**现场总线。核心三件事：

1. 差分物理层
2. ID 仲裁
3. 帧内校验

![CAN 总线基础](/images/1807f836215f48aba0082a5012fcde95.png)

差分电压负责抗干扰：

- **显性（逻辑 0）**：`CANH − CANL ≈ 2 V`，会覆盖隐性
- **隐性（逻辑 1）**：`CANH − CANL ≈ 0 V`
- 两端各挂 **120 Ω** 匹配电阻；断电测总线电阻应 **≈ 60 Ω**

这是仲裁能实现“线与”的物理前提。

![差分电平与终端电阻](/images/6bd01fb7246443a1b9587380b0d4ce7e.png)

## 4. 实测：用示波器看 CAN 波形

使用周立功 CAN200U，自发自收。

### 4.1 接线与通道对应

- **探头必须接在发送端（发出报文的那个通道）**
- 双通道 CAN 卡的两个通道是**物理上独立的两条总线**，不是同一总线的两个抽头
- 通道 0 发帧时，差分电压只出现在 `CANH0 / CANL0`；通道 1 端子上没有信号，探头接过去当然看不到波形
- 示波器地与 CAN 卡地相连（两个地接一起）

> 截图中的实际接法：**CH3 → CANH，CH2 → CANL**；触发源为 **CH3**（CANH 显性电平约 3.5 V，设 3 V 触发合理）。

### 4.2 示波器设置

| 项目 | 设置 |
| --- | --- |
| CH2 / CH3 探头 | `1×`，耦合 `DC`，档位 `1.00 V/div` |
| MATH2 | 运算符 `A − B`；`信源 A = CH3（CANH）`，`信源 B = CH2（CANL）` |
| 数学结果 | `MATH2 = CH3 − CH2 = CANH − CANL` |
| 触发 | 信源 `CH3`，类型 `边沿触发`，`上升沿`，电平 `3.00 V` |
| 时基 | 先看不到波形时把时基调大（如 `10 µs/div`） |

### 4.3 波形怎么对应到 0 / 1

`MATH = CANH − CANL`：

- **高脉冲（≈ 2 V）= 显性位 = 逻辑 `0`**
- **低电平（≈ 0 V）= 隐性位 = 逻辑 `1`**

> 电平高低决定是 `0` 还是 `1`；电平持续时间 ÷ 位宽 = 连续几个 `0` / `1`。

**bit 是时间片**：500 kbit/s 下，`1 bit = 2 µs`。屏幕 `50 µs/div` 时，一格 = 25 bit。每个 bit 占 2 µs，在这 2 µs 内电平要么高、要么低，就是这个 bit 的值。

连续几个相同 bit 会连成**一段宽电平**，看起来像“一个宽脉冲”，但里面包含多个 bit。

## 5. 从波形量到报文帧

### 5.1 常见错误：把高电平平台当成 1 bit

下图的 `4.857 µs` **不是 bit 宽**：

- A 光标在上升沿顶部附近
- B 光标在下降沿顶部附近
- 量到的是**高电平平台宽度**，不是一个 bit

**高电平平台 = 一段连续的显性位（逻辑 `0`）。**

![错误量法](/images/a73c45e32fd34dae90582856a1a39f97.png)

三层含义：

1. **物理层**：`MATH = CANH − CANL ≈ 2 V`，总线被拉成显性
2. **逻辑层**：`500 kbit/s` 下每 `2 µs` 一个位  
   `连续 0 的个数 = 高平台宽度 ÷ 2 µs`
3. **协议层**：宽度只说明“连续几个 0”，属于哪个字段要看它在帧里的位置

若 ZCANPRO 确实配置为 500 kbit/s：

- `1 bit = 2 µs`
- `4.857 µs ÷ 2 µs = 2.43 bit`

不是整数 → 光标没放在等效点上，或波特率不是 500 k。按图粗看这段高电平约 **2 bit（≈ 4 µs）**，低电平约 **1 bit（≈ 2 µs）**，需重测确认。

> 判读口诀：**高低判 0/1，持续时间 ÷ 2 µs 判几个位；边沿取 50% 交叉点，斜边本身不另算。**

![光标 50% 交叉点](/images/ea9dc80609b24955aab69a1fbcad606e.png)

再看一例：`5.7 µs ÷ 2 µs = 2.85 → 取整 3 bit`，相当于三个 `0`。

| 连续 0 个数 | 理论宽度 |
| --- | --- |
| 2 bit | 4.0 µs |
| 3 bit | 6.0 µs |

3 bit 理论 `6.0 µs`，实测 `5.7 µs`，差 `0.3 µs`（5%）。常见来源：

- 光标没精准压在 50% 交叉点
- 两个光标压在不同幅值点（一个 60%，一个 40%）
- 斜边读数 + 照片透视误差

### 5.2 量完整报文帧

![完整帧测量](/images/6366021ec8ac40439b38281d4df135fa.png)

- 理论整帧（含 2 个填充位）：**110 bit = 220 µs**
- 实测 **204.5 µs = SOF → ACK 槽结束（102 bit）**
- 差的 16 µs = **ACK 界定（1 bit）+ EOF（7 bit）**，都是隐性低电平，看不到有效边沿
- 想验证整帧长度：在 ACK 结束点后再加 16 µs，或用 CAN 解码器读，别靠光标找 EOF 终点

> `1 / ΔX = 4.889 kHz` 只是 `204.5 µs` 的倒数，**不是波特率**。CAN 波特率仍是 500 kbit/s。

![帧长度核对](/images/55365a9fcc0b43858700bded50156468.png)

### 5.3 标准数据帧结构

完整 **CAN 标准数据帧** = 7 段；位填充穿插在 SOF ~ CRC 序列之间；帧间隔（IFS）不属于帧。

| 段 | 位数 | 本帧值 | 作用 |
| --- | --- | --- | --- |
| SOF 帧起始 | 1 | `0` | 显性，标志帧开始 |
| 仲裁场 | 12 | ID `00100100011` = `0x123` + RTR `0` | ID 越小优先级越高；RTR=0 表示数据帧 |
| 控制场 | 6 | IDE `0` + r0 `0` + DLC `1000` | IDE=0 标准帧；DLC=8 字节 |
| 数据场 | 64 | `00 11 22 33 44 55 66 77` | 实际有效数据 |
| CRC 场 | 16 | CRC `0x0BD4`（15 bit）+ CRC 界定 `1` | 校验 + 界定 |
| ACK 场 | 2 | ACK 槽 `0` + ACK 界定 `1` | 接收节点应答 |
| EOF 结束 | 7 | `1111111` | 7 个隐性位，帧结束 |

> 去填充：`1 + 12 + 6 + 64 + 16 + 2 + 7 = 108 bit`  
> 本帧填充位：`2 bit`  
> 线上实际：`110 bit = 220 µs`（500 kbit/s）

![帧结构图](/images/45fee7f0fce34b579182c2e6c725dfb3.png)

各字段起始时间（已计入 2 个填充位）：

| 字段 | 位数 | 本帧值 | 起始时间 |
| --- | --- | --- | --- |
| SOF | 1 | `0` | 0 µs |
| ID | 11 | `0x123` = `00100100011` | 2 µs |
| RTR | 1 | `0`（数据帧） | 24 µs |
| IDE | 1 | `0`（标准帧） | 26 µs |
| r0 | 1 | `0` | 28 µs |
| DLC | 4 | `1000` = 8 字节 | 30 µs |
| DATA | 64 | `00 11 22 33 44 55 66 77` | 38 µs |
| CRC | 15 | `0x0BD4` | 170 µs |
| CRC 界定 | 1 | `1` | 200 µs |
| ACK 槽 | 1 | `0`（接收节点应答） | 202 µs |
| ACK 界定 | 1 | `1` | 204 µs |
| EOF | 7 | `1111111` | 206 µs |
| **合计** | **108** | 去填充 | — |
| **位填充** | **+2** | 填充后位序号 22、28 | — |
| **线上实际** | **110 bit** | **220 µs** | — |

### 5.4 用位流验证：ID `0x123` / DATA `00 11 22 33 44 55 66 77`

线上实际位流（含 2 个填充位，共 110 bit）：

```text
00010010001100010000010000010000100010010001000110011010001000101010101100110011101110001011110101001011111111
```

按字段拆开（`[1]` = 填充位）：

```text
SOF     0
ID      00100100011
RTR     0
IDE     0
r0      0
DLC     1000
DATA    00[1]00000[1]000010001001000100011001101000100010101010110011001110111
CRC     000101111010100
CRCdel  1
ACK     0
ACKdel  1
EOF     1111111
```

删掉填充位后，接收端实际解析的 108 bit：

```text
000100100011000100000000000000100010010001000110011010001000101010101100110011101110001011110101001011111111
```

按字段拆开：

```text
0 | 00100100011 | 0 | 0 | 0 | 1000 |
00000000 00010001 00100010 00110011 01000100 01010101 01100110 01110111 |
000101111010100 | 1 | 0 | 1 | 1111111
```

对应关系：

| 字段 | 01 |
| --- | --- |
| SOF | `0` |
| ID | `00100100011` = `0x123` |
| RTR / IDE / r0 | `0 / 0 / 0` |
| DLC | `1000` = 8 |
| DATA | `00 11 22 33 44 55 66 77` |
| CRC | `000101111010100` = `0x0BD4` |
| CRC 界定 | `1` |
| ACK | `0` |
| ACK 界定 | `1` |
| EOF | `1111111` |

位数核对：

```text
108（去填充） + 2（填充） = 110 bit = 220 µs
```

- 已核验：CRC-15 = `0x0BD4`；去填充 108 bit、含填充 110 bit；两组位流与字段拆分一致。
- 文字修正：`XCPCAN / UDSCAN → XCP on CAN / UDS on CAN`，`CANOpen → CANopen`，去掉重复“是是”等笔误。
